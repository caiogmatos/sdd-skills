Install location
~/.claude/skills/ ├── sdd-startup/SKILL.md ← /sdd-startup ├── sdd-bootstrap/SKILL.md ← /sdd-bootstrap ├── sdd-checkup/SKILL.md ← /sdd-checkup ├── sdd-feature/SKILL.md ← /sdd-feature ├── sdd-implement/SKILL.md ← /sdd-implement └── sdd-validate/SKILL.md ← /sdd-validate
The folder name becomes the slash command. The file inside must be named exactly SKILL.md (uppercase) — downloads are named sdd-[name]-SKILL.md, so rename each one when moving it into its folder (see Global Setup for a one-line install command). Claude Code picks up new skills without a restart; if ~/.claude/skills/ didn't exist when the session started, run /reload-skills.
When to use each skill
/sdd-startup
New Project — Greenfield
When you have an idea but no code. Elicits purpose and guides stack selection.
+
use when: starting from scratch never use on existing codebases

Conducts a structured conversation: project purpose → language → framework → data layer → async needs → hosting → testing → hard constraints. For each area Claude presents 2–3 concrete options with one-line trade-offs and a labeled recommendation. You decide. Claude does not default silently. Once all areas are confirmed, generates product.md → tech.md → structure.md → CLAUDE.md (last).

/sdd-bootstrap
Existing Project — Extract Context
When a codebase exists but has no CLAUDE.md or steering docs.
+
use when: no SDD context files exist run once per project run /sdd-checkup first

Scans the codebase and reverse-engineers decisions already made — stack, conventions, folder structure, patterns in use. Asks clarifying questions one at a time for anything ambiguous. Never invents decisions. Generates steering docs first, CLAUDE.md last (to avoid duplicating content from steering docs into the instructions file).

/sdd-checkup
Project Health Audit
When you open an unfamiliar or dormant project and want to know what's missing.
+
use when: starting any session on unknown project safe — reports only, no changes without approval

Scans silently first, then presents a structured report: context files, STATE.md coherence (git log against hash), orphaned specs, metadata freshness, agent files. Suggests fixes ranked Critical → Important → Optional. Applies fixes only after you approve each one, in a safe order. Detects AGENTS.md (Cursor projects) and offers conversion.

/sdd-feature
Spec a Feature
When you have a feature request. Produces requirements.md, design.md, tasks.md.
+
use when: starting any new feature or change requires CLAUDE.md + steering docs to exist first

Three phases with a human approval gate between each. Requirements: asks questions one at a time. Design: cross-references tech.md before writing anything — if the proposed solution needs technology not in the current stack, stops and presents options with trade-offs. Tasks: atomic tasks labeled PARALLEL / SEQUENTIAL / GATE. Implementation starts only after you confirm tasks.md.

/sdd-implement
Implement Features
When tasks.md is approved. Handles one feature or multiple with automatic parallelization.
+
use when: tasks.md approved safe to call in new session — resumes from unchecked tasks /sdd-implement feat-a and feat-b

Parses one or multiple feature names. Checks STATE.md and task checkboxes to detect partial implementations and resume from the right task. For multiple features: builds a file manifest per feature, detects overlap, proposes parallel worktree execution or sequential with rationale. Always presents an execution plan for approval before writing any code. Stack gaps found mid-implementation cause a full stop.

/sdd-validate
Validate a Completed Feature
After all tasks complete. Run in a fresh session — never inline with implementation.
+
use when: all tasks done and committed fresh session required — not inline phase 1 is a hard gate

Four phases. Phase 1 (hard gate): verifies each Acceptance Criterion — any failure stops the skill. Phase 2: audits steering docs for structural changes including stack gap decisions made during design. Phase 3: updates STATE.md with feature status and new HEAD hash. Phase 4: updates CHANGELOG, README, package.json only if they exist and only what's necessary.
