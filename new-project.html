Decision areas, in order
1 Language and runtime
2 Framework
3 Data layer
4 Async work / queues (only if needed)
5 Hosting and deployment
6 Testing (and the test command)

Why the test command matters here: every task in a feature spec names a check that proves it works, and most checks are the project's test command run against the new tests. Settling on it now means every later task has a check it can run.
N·02
What gets generated
Three steering docs, a short CLAUDE.md, STATE.md, and a .gitignore entry
+
P
.claude/steering/product.md: purpose, users, interaction model, what success looks like
T
.claude/steering/tech.md: each stack decision with its reason and the alternatives rejected, plus the build, test and run commands
S
.claude/steering/structure.md: the planned folder layout. It's updated as features land.
C
CLAUDE.md (written last): stack, commands, conventions, NEVER list, and pointers to the steering docs. Under 60 lines.
S
STATE.md: feature status. It gets its first commit hash after your first commit.
G
.gitignore gets .claude/worktrees/, used later when features are built in parallel.
CLAUDE.md ← written last # Stack TypeScript · Node 22 · Fastify · Postgres · Fly.io # Commands - Test: npm test - Run: npm run dev # Conventions - Validate input with Zod at the route - Log with Pino, never console.log # NEVER - In-memory state between requests - Libraries not listed in tech.md # Project context (read when relevant) - .claude/steering/product.md: purpose and users - .claude/steering/tech.md: stack decisions - .claude/steering/structure.md: where code lives - specs/<feature>/ · STATE.md
Why pointers instead of @ imports? An @path import loads the whole file into every session, so splitting files that way saves nothing. The SDD skills read the steering docs when they need them, and CLAUDE.md stays small, which keeps its rules from getting lost.
